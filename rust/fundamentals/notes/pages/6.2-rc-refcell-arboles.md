# 6.2 · Rc, RefCell y árboles

---
layout: center
---

## De listas a árboles

1. Una lista enlazada es estrictamente lineal: cada nodo tiene un único siguiente. Un **árbol binario** relaja esa restricción: cada nodo puede tener hasta dos hijos.

```rust
struct Nodo {
    valor: i32,
    izquierda: Option<Box<Nodo>>,
    derecha: Option<Box<Nodo>>,
}
```

2. Con `Box`, cada nodo sigue siendo dueño exclusivo de sus hijos, igual que en 6.1. Esto funciona mientras el árbol se recorra y modifique desde un único punto de entrada.

layout: center

## Cuando un dueño no basta

Algunos escenarios rompen el supuesto de "un solo dueño":

* Compartir el mismo nodo desde **más de un lugar** (por ejemplo, una estructura que reorganiza o balancea sus propios subárboles).
* Necesitar **mutar** un nodo a través de una referencia compartida, algo que el borrow checker prohíbe en tiempo de compilación con referencias normales.

<div class="important-note">

`Box<T>` resuelve "¿quién es dueño?" con una respuesta única. Cuando la respuesta necesita ser "varios, y a veces hay que modificarlo", Rust ofrece `Rc<RefCell<T>>`.

</div>

layout: center

## Sin `Rc`: dos padres, un hijo

El escenario mínimo: dos nodos que quieren compartir la misma hoja.

```rust
struct Nodo { valor: i32, hijo: Option<Box<Nodo>> }

fn main() {
    let hoja = Box::new(Nodo { valor: 3, hijo: None });

    let padre_a = Nodo { valor: 1, hijo: Some(hoja) };  // se mueve
    let padre_b = Nodo { valor: 2, hijo: Some(hoja) };  // E0382
}
```

<div class="important-note">

Es la regla 2 de ownership: solo un dueño a la vez. Prestar tampoco resuelve, porque
un `&Nodo` no es dueño y tendría que seguir vivo mientras vivan los dos padres, cosa
que la regla 2 del borrow checker obliga a demostrar al compilar.

</div>

## `Rc<T>`: conteo de referencias

`Rc<T>` (*Reference Counted*) permite que varios dueños compartan el mismo valor en el heap, llevando la cuenta de cuántas referencias existen.

```rust
use std::rc::Rc;

let a = Rc::new(5);
let b = Rc::clone(&a); // no copia el 5, incrementa el contador

println!("referencias: {}", Rc::strong_count(&a)); // 2
```

* `.clone()` sobre un `Rc` es barato: solo incrementa un contador, no duplica el dato.
* El valor se libera únicamente cuando el contador llega a cero (el último dueño sale de scope).
* `Rc<T>` por sí solo **no permite mutar** el valor compartido: todas sus referencias son de solo lectura.

layout: center

## Con `Rc`: el mismo árbol

```rust
use std::rc::Rc;

struct Nodo { valor: i32, hijo: Option<Rc<Nodo>> }

fn main() {
    let hoja = Rc::new(Nodo { valor: 3, hijo: None });

    let padre_a = Nodo { valor: 1, hijo: Some(Rc::clone(&hoja)) };
    let padre_b = Nodo { valor: 2, hijo: Some(Rc::clone(&hoja)) };

    println!("dueños de hoja: {}", Rc::strong_count(&hoja));   // 3
}
```

Tres dueños: la variable `hoja` y los dos padres. La hoja se libera cuando el último
de los tres salga de scope.

## `Rc` comparte, pero no deja mutar

```rust
let hoja = Rc::new(Nodo { valor: 3 });
let otro = Rc::clone(&hoja);

otro.valor = 4;   // E0594: cannot assign to data in an `Rc`
```

<div class="important-note">

La regla 2 de ownership quedó atendida, pero sigue en pie la regla 1 del borrow
checker: para mutar hace falta acceso exclusivo, y con dos dueños vivos no lo hay.
`Rc<T>` no implementa `DerefMut`, así que el compilador ni siquiera lo intenta.

</div>

## `RefCell<T>`: mutabilidad en tiempo de ejecución

`RefCell<T>` mueve la verificación de las reglas de *borrowing* (una referencia mutable **o** varias inmutables) del tiempo de compilación al tiempo de ejecución.

```rust
use std::cell::RefCell;

let celda = RefCell::new(5);

*celda.borrow_mut() += 1;
println!("{}", celda.borrow()); // 6
```

<div class="important-note">

Si en ejecución se viola la regla, el programa hace *panic* en vez de no compilar. Dos `borrow_mut()` vivos a la vez abortan con *RefCell already borrowed*.

</div>

---
layout: center
---

## `Rc<RefCell<T>>`: compartir y mutar

Combinando ambos, un árbol puede tener nodos con **múltiples dueños** que además pueden mutarse:

```rust
use std::cell::RefCell;
use std::rc::Rc;

struct Nodo {
    valor: i32,
    izquierda: Option<Rc<RefCell<Nodo>>>,
    derecha: Option<Rc<RefCell<Nodo>>>,
}
```

* `Rc` responde "¿quién puede acceder a este nodo?" → varios.
* `RefCell` responde "¿puede alguien modificarlo?" → sí, verificado en ejecución.

layout: center

## El mismo hijo, mutado desde otro dueño

```rust
use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    let hoja = Rc::new(RefCell::new(Nodo { valor: 3 }));
    let otro = Rc::clone(&hoja);          // segundo dueño

    otro.borrow_mut().valor = 4;          // muta a través del segundo

    println!("{}", hoja.borrow().valor);  // 4: es el mismo nodo
}
```

<div class="important-note">

Ninguna regla se rompió. La 2 de ownership la absorbe `Rc` con su contador, y la 1
del borrow checker la absorbe `RefCell` verificándola en ejecución. Es la misma
regla; mover la comprobación es lo que cuesta.

</div>

layout: center

## Lo que cuesta mover la comprobación

`RefCell<T>` no es un envoltorio transparente. La regla es la misma, pero
verificarla en ejecución deja huella en cuatro frentes.

<div class="text-sm cp-table-compact">

| Frente | Con referencias | Con `RefCell<T>` |
| :--- | :--- | :--- |
| Memoria | ninguna | 8 bytes de bandera: `RefCell<i32>` mide 16 |
| Ejecución | ninguna | leer, escribir y ramificar en cada `borrow` |
| Fallo | error de compilación | *panic*, o `Err` con `try_borrow_mut` |
| Hilos | según el tipo | nunca: `RefCell<T>` no es `Sync` (8.2 Send y Sync) |

</div>

Es la excepción a 4.0 Abstracciones de costo cero: aquí la abstracción sí cobra.

## El préstamo dura lo que dura el guard

Un ***guard*** es un valor que sostiene un permiso y lo devuelve al destruirse, en
su `Drop`. `borrow()` devuelve un `Ref<T>` y `borrow_mut()` un `RefMut<T>`.

```rust
let celda = RefCell::new(vec![1, 2, 3]);

let primero = celda.borrow();   // el guard vive hasta el final del scope
celda.borrow_mut().push(4);     // panic: RefCell already borrowed

println!("{primero:?}");
```

<div class="important-note">

Sin el `println!` final, el guard moriría antes por NLL (3.6 Lifetimes) y el
programa correría. El préstamo vale hasta donde llegue el guard.

</div>

El `x if cond` de 2.4 Patrones, que también se llama *guard*, no tiene relación.

## Recorridos: preorden, inorden, postorden

Los tres recorridos clásicos visitan los mismos tres elementos (nodo, izquierda, derecha), solo cambia el orden:

<div class="grid grid-cols-3 gap-x-6 mt-4 text-sm">

<div class="[&_pre]:my-0">

**Preorden**

```rust
fn preorden(n: &Nodo) {
    visitar(n);
    if let Some(i) = &n.izquierda {
        preorden(i);
    }
    if let Some(d) = &n.derecha {
        preorden(d);
    }
}
```

nodo → izq → der

</div>

<div class="[&_pre]:my-0">

**Inorden**

```rust
fn inorden(n: &Nodo) {
    if let Some(i) = &n.izquierda {
        inorden(i);
    }
    visitar(n);
    if let Some(d) = &n.derecha {
        inorden(d);
    }
}
```

izq → nodo → der

</div>

<div class="[&_pre]:my-0">

**Postorden**

```rust
fn postorden(n: &Nodo) {
    if let Some(i) = &n.izquierda {
        postorden(i);
    }
    if let Some(d) = &n.derecha {
        postorden(d);
    }
    visitar(n);
}
```

izq → der → nodo

</div>

</div>

## Qué indirección pide cada algoritmo

La mayoría de los algoritmos sobre árboles binarios no necesitan `Rc` ni `RefCell`.
Solo los pide la forma de la estructura, no la operación.

<div class="text-sm cp-table-compact">

| Caso | Alcanza con |
| :--- | :--- |
| buscar, insertar, borrar en un BST | `Option<Box<Nodo>>`, mutando por `&mut` desde la raíz |
| los tres recorridos de arriba | `&Nodo`: son de solo lectura |
| rotaciones de AVL o rojo-negro | `Box` y `take()`: una rotación mueve subárboles |
| que un nodo apunte a su padre | `Rc<RefCell<T>>` hacia abajo, `Weak<T>` hacia arriba |
| un nodo con varios padres: DAG, trie | `Rc<RefCell<T>>` |

</div>

<div class="important-note">

`Weak<T>` es un `Rc` que no cuenta como dueño: no impide liberar el valor, y por eso
el enlace al padre no cierra el ciclo que filtraría memoria. Se saca con
`Rc::downgrade` y se cobra con `.upgrade()`, que devuelve `Option`.

</div>

## Cierre: ¿cuál indirección usar?

<div class="important-note">

* **`Box<T>`** — un único dueño, estructura estrictamente jerárquica (listas, árboles simples sin reestructuración).
* **`Rc<T>`** — múltiples dueños de solo lectura.
* **`Rc<RefCell<T>>`** — múltiples dueños que además necesitan mutar el valor compartido.
* **`Arc<Mutex<T>>`** — lo mismo, pero entre hilos: `Rc` y `RefCell` son mono-hilo y el compilador los rechaza al cruzar a otro hilo. Es el tema de la sección 8.

</div>

Criterio: número de dueños, y necesidad de mutar después de compartir.
