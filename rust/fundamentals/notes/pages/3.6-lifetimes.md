# 3.6 · Lifetimes

---
layout: center
---

## Para qué existen

El *borrow checker* vigila dos condiciones (3.3 Borrowing):

<div class="important-note">

1. Una referencia mutable **o** varias inmutables, nunca las dos a la vez.
2. **Toda referencia debe ser siempre válida.**

</div>

La primera se comprueba mirando qué préstamos coexisten. La segunda no: exige saber
**hasta cuándo vive cada dato y hasta cuándo se usa cada referencia**. Los lifetimes
son la herramienta con la que el compilador mide eso.

---
layout: center
---

## Lifetimes concretos ($L$)

Un lifetime concreto es la **región de código** donde una referencia está viva.

* Va desde donde se crea la referencia hasta su **último uso** (*Non-Lexical Lifetimes*, desde Rust 2018), no hasta la llave que cierra el bloque.
* Distinción clave: el *scope del valor* sí termina en `}`, y ahí corre `Drop`. El lifetime de la referencia termina antes, en cuanto deja de usarse.
* No se escriben: el compilador los calcula solo.

---
layout: center
---

## Lifetimes genéricos ($'a$)

`'a` **no es una duración**. Es el nombre de una incógnita: una restricción que
relaciona varias referencias entre sí y que el compilador resuelve.

<div class="important-note">

`fn f<'a>(s: &'a str, t: &'a str) -> &'a str` no dice *"estas referencias viven
tanto"*. Dice: *"la salida no puede vivir más que la más corta de las entradas"*.

</div>

Hacen falta cuando una función devuelve una referencia: el compilador no puede
adivinar de cuál entrada salió, y `'a` es la forma de decírselo.

---
layout: center
---

## Dónde hacen falta

1. **Cuando una función devuelve una referencia** y hay más de una entrada: el compilador no puede deducir de cuál salió.
2. **Cuando una struct guarda una referencia**: hay que declarar que la struct no puede sobrevivir al dato que apunta.

Fuera de esos dos casos casi nunca se escriben: las reglas de elisión los deducen.

---
layout: center
---

## Caso 1 · una función devuelve una referencia

Con dos entradas prestadas, el compilador no puede deducir de cuál sale el retorno.
Hay que decírselo.

<div class="important-note">

*this function's return type contains a borrowed value, but the signature does not
say whether it is borrowed from `a` or `b`*

</div>

## Caso 2 · una struct guarda una referencia

La struct no puede sobrevivir al dato que apunta. El lifetime lo declara en el tipo.

<div class="important-note">

Alternativa de diseño: cambiar `&'a str` por `String` y que la struct sea **dueña**
de su texto. Muchas veces es la respuesta correcta, y evita el lifetime por completo.

</div>

---
layout: center
---

````md magic-move

```rust
struct User {
    age: i32,
    name: & str
}

fn main() {
    let n = "Giovanny";
    let usr = User {
        age: 32,
        name: n
    };
    println!("Mi nombre es {} y tengo {} años", usr.name, usr.age);
}
```

}
```
````

## Las operaciones

Comparar lifetimes es comparar **regiones de código**, no números.

<div class="text-sm cp-table-compact">

| Notación | Se lee |
| :--- | :--- |
| $L(x)$ | la región donde la referencia `x` está viva |
| $L(s) \le L(t)$ | la región de `s` cabe dentro de la de `t` |
| $min(L(s), L(t))$ | la región que **termina primero**: lo común a las dos |
| $max(L(r))$ | el punto más tardío en el que se usa `r` |

</div>

No miden segundos: eligen entre regiones anidadas. La más corta impone el límite,
como el eslabón más débil de una cadena.

---
layout: center
---

## Ecuación general de los lifetimes

<div class="important-note">

Sean $s$ y $t$ las entradas de una función y $r$ la salida. El borrow checker
resuelve:

$$ 'a = min(L(s),\ L(t)) \quad \text{y verifica} \quad max(L(r)) \le\ 'a $$

`'a` vale lo que dure la entrada más corta, y el último uso de la salida tiene que
caer dentro de esa región.

</div>

Notación propia: en la documentación de Rust no vas a encontrar $min$ ni $max$ sobre
lifetimes. El modelo predice bien, pero conviene saber que es un atajo tuyo.

## Caso válido: los dos datos sobreviven al uso

<div class="grid grid-cols-2 gap-x-8 items-center mt-2">

  <div class="[&_pre]:my-0">

```rust
fn foo<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let s = String::from("hello");  // ①
    let t = String::from("hola");   // ②
    let r = foo(&s, &t);            // ③
    println!("{r}");                // ④
}
```

  </div>

  <div class="text-sm space-y-3">

**① Leer las regiones**

* $L(s):$ de ① al final
* $L(t):$ de ② al final
* $L(r):$ de ③ a ④, su último uso

**② Resolver la incógnita**

$$ 'a = \min(L(s), L(t)) $$

Las dos entradas llegan al final de `main`, así que `'a` puede llegar hasta ④.

**③ Verificar**

$$ \max(L(r)) = ④ \ \le\ 'a \quad \color{green}{✓} $$

  </div>

</div>

## Caso inválido: un dato muere antes

<div class="grid grid-cols-2 gap-x-8 items-center mt-2">

  <div class="[&_pre]:my-0">

```rust
fn main() {
    let r: &str;
    let s = String::from("hello");  // ①
    {
        let t = String::from("hola");  // ②
        r = foo(&s, &t);  // ③
    }  // ④ muere t
    println!("{r}");  // ⑤
}
```

  </div>

  <div class="text-sm space-y-3">

**① Leer las regiones**

* $L(s):$ de ① al final
* $L(t):$ de ② a ④, muere en la llave
* $L(r):$ de ③ a ⑤

**② Resolver la incógnita**

$$ 'a = \min(L(s), L(t)) = L(t) $$

`t` es la entrada que muere primero, en ④. `'a` no puede pasar de ahí.

**③ Verificar**

$$ \max(L(r)) = ⑤ \ >\ ④ \quad \color{red}{✗} $$

  </div>

</div>

## Dos formas distintas de no compilar

Los errores de esta sección vienen de dos sitios que conviene no confundir.

<div class="text-sm cp-table-compact">

| | Falta información | Falla la verificación |
| :--- | :--- | :--- |
| Error típico | `E0106` *missing lifetime specifier* | `E0597` *does not live long enough* |
| Qué dice | *"no puedo saber de dónde sale esta referencia"* | *"lo comprobé, y no se cumple"* |
| Se arregla | anotando `<'a>` en la firma o la struct | cambiando el código: acortar el uso o dejar de prestar |

</div>

<div class="important-note">

El primero **no dice que el programa esté mal**: dice que al borrow checker le faltan
herramientas para juzgarlo. El segundo sí es un veredicto. Anotar lifetimes nunca
convierte un programa inválido en válido, solo permite que se le evalúe.

</div>

---
layout: center
---

## Lo que la ecuación captura

<div class="important-note">

El error no es *"`t` se destruyó"*. Es que **`r` prometió durar lo que dure `'a`**, y
`'a` quedó atado a la entrada más corta. Devolver una referencia es firmar un contrato
sobre el dato de otro.

</div>

Por eso el arreglo casi nunca es alargar el lifetime: es **acortar el uso de `r`**
—meter el `println!` dentro del bloque— o **dejar de prestar** y devolver un `String`
propio.

## Seguridad de memoria en Rust

Al trabajar en conjunto, el sistema de **Ownership**, el **Borrow Checker** y las reglas de **Lifetimes** eliminan los errores de gestión de memoria más comunes de la industria:

* **Punteros nulos:** Rust garantiza que toda referencia apunte siempre a un lugar válido en memoria.
* **Desbordamientos de búfer:** Valida estrictamente que las lecturas y escrituras ocurran dentro de los límites de los arreglos.
* **Punteros colgados / Doble liberación:** Erradicados por completo gracias al control estricto de ámbitos de vida.

---
layout: center
---

* **Carreras de datos (Data races):** Impide el acceso simultáneo y desordenado a un mismo dato en entornos multihilo.
* **Comportamientos indefinidos:** El compilador rechaza cualquier zona gris de la memoria (*undefined behavior*).
* **Cero Garbage Collector:** No se necesita pausar el programa en ejecución; todo se resuelve al compilar.

Rust traslada estas garantías al **tiempo de compilación**. Un programa que compila sin `unsafe` está libre de accesos inválidos a memoria. Las fugas no entran en esa garantía: un ciclo de `Rc` filtra memoria y sigue siendo código seguro.
