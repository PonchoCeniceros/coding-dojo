# 9.5 · async o hilos

---
layout: center
---

## La pregunta correcta: ¿espera o calcula?

<div class="text-sm cp-table-compact">

| La tarea | Herramienta | Por qué |
| :--- | :--- | :--- |
| espera red, disco o base de datos | **async** | miles de esperas sobre pocos hilos |
| ocupa CPU sin parar | **hilos**, o el crate `rayon` | no hay nada que ceder mientras se calcula |
| es una tubería productor/consumidor | **canales** | el modelo ya encaja |

</div>

Una API web es lo primero: casi todo su tiempo lo pasa esperando a la base de datos.
Un procesamiento de datos con Polars es lo segundo.

layout: center
---

## El error clásico: bloquear dentro de async

```rust
async fn manejador() {
    let resultado = calculo_pesado();   // ocupa el hilo del runtime
    println!("{resultado}");
}

fn calculo_pesado() -> u64 {
    (1..50_000_000u64).sum()
}
```

<div class="important-note">

Esto compila y arruina el servidor. Ese hilo del runtime no puede atender ninguna
otra tarea mientras calcula, y son pocos. El síntoma es un servicio que se congela
bajo carga sin que ningún error aparezca.

</div>

## Mandar el cálculo a otro lado

```rust
async fn manejador() {
    let resultado = tokio::task::spawn_blocking(|| {
        (1..50_000_000u64).sum::<u64>()
    })
    .await
    .unwrap();

    println!("{resultado}");
}
```

`spawn_blocking` entrega el trabajo a un pozo de hilos aparte, reservado justo para
esto, y devuelve un futuro que se puede esperar sin trabar el runtime.

## Lo que hay que llevarse

<div class="important-note">

**async no acelera nada.** No hace que un cálculo termine antes; hace que un hilo
que iba a estar esperando pueda atender otra cosa. La ganancia es de escala, no de
velocidad.

Para ir más rápido en un cálculo, lo que sirve es el paralelismo de datos.

</div>
