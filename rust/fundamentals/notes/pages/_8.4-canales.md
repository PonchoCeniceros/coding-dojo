# Canales

---
layout: center

## Comunicar en vez de compartir

Un canal mueve valores de un hilo a otro. Como el valor **se mueve**, nunca hay dos
hilos tocando el mismo dato, y el problema de sincronización desaparece en vez de
resolverse con candados.

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        tx.send(String::from("listo")).unwrap();
    });

    println!("{}", rx.recv().unwrap());
}
```

`mpsc` es *multiple producer, single consumer*: se puede clonar el emisor, no el
receptor.

## Varios emisores

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    for i in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || { tx.send(i * 10).unwrap(); });
    }
    drop(tx);                    // sin esto, el bucle no termina

    for recibido in rx {
        println!("{recibido}");
    }
}
```

<div class="important-note">

El receptor es un iterador que termina cuando **todos** los emisores mueren. El `tx`
original sigue vivo en `main`, así que hay que soltarlo a mano.

</div>

## Cuál usar

<div class="text-sm cp-table-compact">

| | Canal | `Arc<Mutex<T>>` |
| :--- | :--- | :--- |
| Forma | pasar mensajes | memoria compartida |
| Riesgo de bloqueo | ninguno | sí, si se toman candados en distinto orden |
| Encaja con | una tubería de trabajo, productor/consumidor | un estado que muchos leen y escriben |

</div>

<div class="important-note">

Regla práctica: **canal por default**, porque el compilador hace casi todo el
trabajo. `Arc<Mutex<T>>` cuando de verdad hay un estado central que varios hilos
necesitan ver, como un contador de métricas o una caché.

</div>
