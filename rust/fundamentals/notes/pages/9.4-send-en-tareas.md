# 9.4 · Send en las tareas

---
layout: center
---

## Una tarea puede cambiar de hilo

El runtime mueve tareas entre sus hilos para balancear la carga. Por eso
`tokio::spawn` exige que el futuro sea `Send` y `'static`: las mismas garantías de
8.2, ahora sobre algo que se pausa y se reanuda.

<div class="text-sm cp-table-compact">

| Requisito | Por qué |
| :--- | :--- |
| `Send` | la tarea puede reanudarse en otro hilo |
| `'static` | la tarea puede vivir más que quien la lanzó |

</div>

---
layout: center
---

## Un futuro es `Send` si todo lo que cruza un `.await` lo es

```rust
use std::sync::{Arc, Mutex};

async fn otra() {}

async fn tarea(m: Arc<Mutex<i32>>) {
    let guard = m.lock().unwrap();
    otra().await;              // `guard` sigue vivo aquí
    println!("{}", *guard);
}

#[tokio::main]
async fn main() {
    tokio::spawn(tarea(Arc::new(Mutex::new(0))));  // el error sale aquí
}
```

<div class="important-note">

`error: future cannot be sent between threads safely`. `MutexGuard` no es `Send`
y aquí sobrevive al `.await`. La función sola compila: el error sale al hacer
`spawn`.

</div>

layout: center

## Los dos arreglos

<div class="grid grid-cols-2 gap-x-6 mt-4 w-full text-left">
  <div>
    <span class="text-xs cp-ok font-bold block mb-1">Soltar el candado antes</span>

```rust
use std::sync::Mutex;
async fn otra() {}

async fn tarea(m: &Mutex<i32>) {
    let v = {
        let g = m.lock().unwrap();
        *g
    };                    // aquí muere el guard
    otra().await;
    println!("{v}");
}
```

  </div>

  <div>
    <span class="text-xs cp-ok font-bold block mb-1">Usar el mutex del runtime</span>

```rust
// tokio::sync::Mutex
// su guard sí es Send, y
// `lock()` es asíncrono:
//
// let g = m.lock().await;
// otra().await;
// println!("{}", *g);
```

  </div>
</div>

<div class="important-note">

El primero es preferible: soltar el candado antes de esperar es más rápido y evita
retener el recurso durante una operación de red. El mutex asíncrono solo hace falta
cuando el estado debe permanecer bloqueado a través del `.await`.

</div>

## Cómo se lee ese error

El compilador apunta al `spawn`, pero el detalle útil viene después:

```text
note: future is not `Send` as this value is used across an await
    let guard = m.lock().unwrap();
        ----- has type `MutexGuard<'_, i32>` which is not `Send`
    otra().await;
           ^^^^^ await occurs here, with `guard` maybe used later
```

<div class="important-note">

La receta es siempre la misma: buscar qué valor está vivo a ambos lados del `.await`
y acortarle la vida. Los culpables habituales son `Rc`, `RefCell` y los guards de
`std::sync`.

</div>
