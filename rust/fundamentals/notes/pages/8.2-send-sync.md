# 8.2 · Send y Sync

---
layout: center
---

## El ownership, aplicado a los hilos

Son dos traits marcadores: no tienen métodos, solo describen qué es seguro hacer con
un tipo entre hilos. El compilador los implementa solo, y con ellos verifica las
carreras de datos **en compilación**.

<div class="text-sm cp-table-compact">

| Trait | Significa |
| :--- | :--- |
| `Send` | el valor se puede **mover** a otro hilo |
| `Sync` | el valor se puede **compartir** por referencia entre hilos (`&T` es `Send`) |

</div>

Casi todo lo del deck es las dos cosas. Lo interesante son las tres excepciones.

---
layout: center
---

## `Rc` no cruza; `Arc` sí

```rust
use std::rc::Rc;
use std::thread;

fn main() {
    let contador = Rc::new(5);

    thread::spawn(move || {
        println!("{contador}");
    });
}
```

<div class="important-note">

`error[E0277]: Rc<i32> cannot be sent between threads safely`. `Rc` lleva su cuenta
de referencias sin sincronizar (6.2 Rc, RefCell y árboles): dos hilos incrementándola a la vez la
corromperían. `Arc` es el mismo tipo con la cuenta atómica, y por eso sí es `Send`.

</div>

layout: center
---

## Las tres excepciones que vas a encontrar

<div class="text-sm cp-table-compact">

| Tipo | `Send` | `Sync` | Por qué |
| :--- | :---: | :---: | :--- |
| `Rc<T>` | no | no | cuenta de referencias sin sincronizar |
| `RefCell<T>` | sí | **no** | su chequeo de préstamos no es atómico |
| `MutexGuard<T>` | no | sí | debe liberarse en el hilo que lo tomó |

</div>

El reemplazo para hilos es directo: `Rc` → `Arc`, y `RefCell` → `Mutex` o `RwLock`, que llegan en 8.3.

---
layout: center
---

## Se propagan solos

Un tipo propio es `Send` si todos sus campos lo son, y `Sync` si todos son `Sync`.
No hay que implementarlos, y casi nunca hay que nombrarlos.

```rust
struct Config {
    nombre: String,
    reintentos: u32,
}
// Config es Send y Sync: String y u32 lo son
```

<div class="important-note">

Por eso el error no aparece donde está el problema, sino donde el valor cruza al
hilo. Cuando un framework web rechace un handler con *"future is not `Send`"*, la
causa suele ser un `Rc` o un `RefCell` escondido varios niveles adentro.

</div>
